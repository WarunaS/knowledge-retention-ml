Detailed Architecture Plan

AI Knowledge Retention Agent – a data-and-modelling plane that learns to classify developer–AI knowledge, and a knowledge-application plane that stores, retrieves and delivers it

Version 2.1 · Revised 11 November 2026 · Companion documents: Research Plan, Detailed Technical Plan · Code: knowledge-retention-ml

1. Architectural Objective

The architecture has two jobs. First, it must support a reproducible machine-learning study: acquire public developer–LLM corpora, label them on two axes, train and compare classifiers, and measure how the best model transfers to real agentic development logs. Second, it must turn the classifier's output into reusable organisational knowledge: extract knowledge cards, store and index them, and deliver them to a successor through an AI agent.

The pipeline is: corpus acquisition → filtering and preprocessing → two-axis labelling → model training and evaluation → classification of segments → knowledge extraction → storage and indexing → retrieval and delivery (ask-predecessor agent and handover packs) → evaluation. The modelling steps follow the ML project lifecycle set out in section 5 of the Research Plan. The architecture is deliberately light, explainable and local-first. It is a research prototype, not an enterprise platform.

2. Architectural Principles

Experiment-first

  • Every modelling step produces a number against a baseline
  • Splits, seeds and dataset versions are fixed and recorded
  • The trained model is an artefact with a version, metrics and a model card

Data-first

  • Filtering, deduplication and labelling quality matter more than model size
  • Human gold labels are the only basis for reported results
  • Provenance from card back to source turn is preserved everywhere

Local-first and privacy-aware

  • The research question is whether a local model can replace a cloud LLM for classification
  • Cloud LLM calls are confined to labelling and extraction, never to serving
  • Own logs are used only with written consent and only for the transfer test

Retrieval-first value

  • Classified and extracted knowledge is useful only if a successor can find it
  • Labels drive retrieval filters and card framing
  • Person, role and project are metadata filters recorded at ingestion, never model outputs
  • Delivery goes through the successor's own AI client via MCP

Minimal viable prototype

  • Vector index first; the relationship graph stays lightweight
  • No live capture; an optional knowledge map only if time allows
  • One shared classifier; no model per person or per role
  • Every component is replaceable behind a small interface

4. Layered Architecture

4.1 Data acquisition layer

  • Download gated public corpora after licence acceptance
  • Record dataset name, version, date and licence in a manifest
  • Keep raw files immutable for auditing
  • Attach author, role, project and date where known: the repository for DevGPT and agent runs, the team directory for consented own logs

4.2 Data preparation layer

  • Language, toxicity and turn-count filters
  • Keyword relevance filter for technical and requirements conversations, with a hand-checked precision estimate
  • Redaction of own logs, MinHash near-duplicate removal, normalisation, segmentation into exchanges with the previous exchange as context

4.3 Labelling layer

  • Codebook as the single definition of both label axes
  • LLM labelling with schema-constrained output for the training pool
  • Annotation tooling for the human gold set and agreement statistics

4.4 Modelling layer

  • Baselines: majority, TF-IDF with logistic regression, embeddings with logistic regression
  • Fine-tuned small transformer, multi-label heads for domain and knowledge type
  • Few-shot SetFit variant, ablations, learning curve, teacher comparison

4.5 Model registry and serving layer

  • Versioned weights, training config, metrics and model card
  • Classification service loads the registered model and scores segments with per-label probabilities and thresholds tuned on validation
  • Runs on CPU; no cloud call at inference time

4.6 Knowledge extraction layer

  • Only segments the classifier flags as knowledge-bearing are extracted
  • Card template chosen by knowledge type; domain labels attached
  • Faithfulness check: evidence quoted verbatim from the source and at least half of the summary's content words found in the source; cards failing either are rejected with the reason

4.7 Storage and indexing layer

  • Metadata database for cards, labels, provenance and consent
  • Vector index of card embeddings for semantic search
  • Lightweight graph of problem → decision → tool → domain edges, in-process

4.8 Retrieval and delivery layer

  • Semantic retrieval filtered by domain, knowledge type, person, role and project
  • Optional one-hop graph expansion for connected reasoning
  • REST API and an MCP tool so a successor asks from inside their own AI client
  • Handover packs per person and per project; optional knowledge map of coverage and single-person dependency, with no ranking of individuals

4.9 Evaluation layer

  • Classification, transfer, retrieval and successor-task measurement
  • Results tables and plots generated from stored predictions, not by hand
  • Every reported number traceable to a run id

5. Core Components

5.1 Corpus loader

  • One adapter per dataset producing the shared Conversation record
  • Carries source, licence and modality (conversational or agentic)
  • Carries author, role, project and date when the source provides them

5.2 Filter and preprocessor

  • Rule filters and keyword relevance; a zero-shot classifier only if hand-checked precision is low
  • Deduplication, normalisation, segmentation, tokenisation checks

5.3 Labelling service

  • Prompts the LLM with the codebook and returns schema-valid labels
  • Stores raw LLM output for auditability

5.4 Annotation set

  • Gold labels from two raters with an overlap subset
  • Kappa computation, adjudication log, codebook revision history

5.5 Trainer and experiment runner

  • Configurable runs for baselines, fine-tuning, ablations
  • Fixed seeds, conversation-level splits, metrics written per run

5.6 Classification service

  • Loads the registered model and scores new segments
  • Emits label probabilities and a knowledge-bearing flag

5.7 Extraction engine

  • Claude writes typed knowledge cards for public sources; own-log segments use a local extractive backend (no LLM) so their content never reaches a cloud model
  • Faithfulness check and rejection of ungrounded cards

5.8 Knowledge repository

  • Metadata database, vector index, lightweight graph
  • Provenance from card to segment to source conversation

5.9 Query agent

  • Accepts a question, retrieves cards, answers with citations
  • Can be narrowed to a person, role or project
  • Exposed as REST and as an MCP tool

5.10 Handover pack generator

  • Selects cards for one person or one project
  • Writes a decision log in date order, procedures, domain notes, and context and constraints, each entry linked to its source

  • If inter-annotator agreement is below 0.6, the codebook is revised and the labelling loop re-runs once. Both versions are reported.
  • Only a model evaluated on the gold set can be registered. Weak-label validation scores are used for model selection, never for reporting.
  • The transfer test runs once on the final registered model so that it cannot be tuned against the own-log sample.

7. Data Flow

  1. Corpus loaders read the public datasets and emit Conversation records with source, modality, and author, role, project and date where known.
  2. The filter keeps English, non-toxic, multi-turn conversations that are technical or about requirements.
  3. The preprocessor removes near-duplicates, normalises text and cuts conversations into Segment records with one turn of context.
  4. Exploratory analysis describes the corpus and BERTopic clusters seed the domain taxonomy.
  5. The labelling service assigns weak labels to the training pool; two raters produce the gold set and agreement is computed.
  6. The experiment runner trains baselines and the fine-tuned model on conversation-level splits and writes metrics per run.
  7. The best model is registered and loaded by the classification service.
  8. The classification service scores segments; flagged segments go to the extraction engine, which writes typed knowledge cards.
  9. Cards are stored with provenance, embedded into the vector index, and linked in the lightweight graph.
  10. The query agent retrieves cards for a successor's question, optionally narrowed to a person, role or project, and answers with citations via REST or MCP.
  11. The handover pack generator assembles a pack per person or per project from the stored cards.
  12. The evaluation layer computes classification, transfer, retrieval and successor-task results from stored predictions and logs.

11. Design Constraints for the PoC

  • Public corpora only for training; own logs only for the transfer test, with consent
  • Models must train on a free GPU or a laptop CPU within hours
  • Human gold set is the only basis for reported results
  • Vector index first; the graph stays in-process and lightweight unless the retrieval evaluation shows it is needed
  • Cloud LLM used only for labelling and extraction of public data, within the stated budget; extraction from own logs uses the local model
  • One shared classifier; no model is trained per person or per role
  • Person-level demonstrations use consented own logs or clearly labelled synthetic personas
  • Live capture is out of scope for this iteration; the knowledge map is optional
The knowledge graph and MCP delivery are kept because they are part of the group's agreed design and the storage sub-topic. They are implemented thinly so they do not compete for time with the modelling work.

12. Security, Ethics and Privacy Considerations

  • Use only public corpora whose licences permit research use, and cite them
  • Do not attempt to identify any user in the public corpora
  • Own logs: written consent per member, redaction of secrets and personal data before labelling, deletion after the study
  • No raw conversation content is sent to a cloud LLM from own logs; only the public-trained model and the local extraction model run on them
  • Frame the system as knowledge retention and onboarding support, never as employee monitoring
  • Individuals are never ranked or scored; the knowledge map shows coverage and single-person dependency only
  • Author ids are pseudonymous; all of one person's cards can be deleted on request without retraining
  • Record provenance so that any card can be traced and removed on request

13. Recommended Final Architecture Outcome

The final system demonstrates a complete lifecycle: public developer–LLM corpora are filtered and labelled, a small classifier is trained and shown to approach an LLM teacher on human-labelled data, its transfer to real agentic logs is measured, and its output drives extraction, storage, retrieval and delivery of knowledge to a successor through cited answers and handover packs. This satisfies the MSc research objective with a measurable contribution, and leaves deployment, monitoring and live capture as clearly stated future work.
