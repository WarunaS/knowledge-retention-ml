AI Knowledge Retention System

Research plan: learning to identify and classify organisational knowledge in developer–AI conversations, and reusing it through a retrieval agent

Version 2 · Revised 13 October 2026 · Companion documents: Detailed Architecture Plan, Detailed Technical Plan

1. Project Aim

To design, train and evaluate a classifier that identifies knowledge-bearing segments in developer–LLM conversations and labels them on two axes, technical domain and knowledge type, and then to demonstrate that the extracted knowledge can be reused by a successor through a retrieval agent. The project treats the trained model as the research contribution and the retrieval agent as the application that consumes it.

Primary research question (RQ1) Can a small, locally trained model identify and classify organisational knowledge in developer–AI conversations as well as a large LLM, so that interaction logs can be processed without leaving the organisation?
Secondary questions
  • RQ2: Which technical domains and knowledge types occur in developer–LLM conversations, and how often?
  • RQ3: Does a model trained on public chatbot logs transfer to real agentic development logs?
  • RQ4: Do the extracted knowledge cards help a successor answer questions about unfamiliar work?
Hypotheses
  • H1: A fine-tuned small transformer beats lexical and embedding baselines on macro-F1.
  • H2: The fine-tuned model comes within five F1 points of the LLM teacher on the human-labelled test set.
  • H3: Including the preceding conversation turn as context improves classification over the single turn alone.
Scope strategy Offline study on public developer–LLM corpora, with a small consented sample of the team's own agentic tool logs used only for a transfer test. No live capture, no production deployment. Live capture is future work that the trained model would serve.

2. Motivation and Novelty

The problem

  • Developers increasingly do their reasoning inside agentic AI tools such as Claude Code, Cursor, Copilot and Codex
  • Decisions, trade-offs and problem decompositions that once reached wikis and colleagues now sit in unread log files
  • When a developer leaves, this knowledge leaves with them

Theoretical anchor

  • SECI model (Nonaka, 1994): an LLM conversation forces externalisation of tacit knowledge
  • Polanyi (1966): people know more than they can tell, but they tell more to an AI than to a form
  • Davenport and Prusak (1998): knowledge has value only when it can be found and applied

What is new

  • Agent memory work (A-Mem, MemGPT) gives one agent memory of its own past; this project transfers one person's knowledge to a different person
  • Prior tacit knowledge studies elicit knowledge by interview; this project mines it passively from existing interaction logs
  • No published taxonomy or classifier covers knowledge in agentic development logs with tool calls

4. Research Stages

1. Literature review

  • Knowledge management and the tacit/explicit distinction
  • Agent memory, retrieval-augmented generation and MCP delivery
  • LLM-assisted annotation and knowledge distillation

2. Data acquisition and exploratory analysis

  • Accept dataset licences, download, record versions
  • Describe turn counts, lengths, languages and topic clusters
  • Estimate the share of knowledge-bearing conversations

3. Preprocessing and filtering

  • English, non-toxic, at least two exchanges
  • Technical relevance filter with a hand-checked precision estimate
  • Near-duplicate removal, normalisation, segmentation into turn windows

4. Taxonomy and labelling

  • Codebook with definitions, examples and observable cues
  • LLM weak labels for the training pool
  • Human gold set with inter-annotator agreement and adjudication

5. Model training and experiments

  • Baselines, fine-tuned classifier, few-shot variant, teacher comparison
  • Ablations for context and training-set size
  • Conversation-level splits, significance tests, confidence intervals

6. Knowledge extraction and storage

  • LLM extraction of knowledge cards from segments the classifier flags
  • Faithfulness check of each card against its source segment
  • Vector index plus a lightweight relationship graph

7. Retrieval and agent layer

  • Semantic retrieval filtered by domain and knowledge type
  • Grounded answers with citations to cards and source turns
  • Delivery through an API and an MCP tool so a successor can ask instead of search

8. Evaluation and reporting

  • Classification results, transfer gap, retrieval relevance
  • Small successor task with and without the knowledge cards
  • Contribution, limitations and future work including live capture

5. Two-Axis Knowledge Taxonomy

Every segment receives labels on both axes. Both axes are multi-label because one segment can carry, for example, a backend decision that is also a security procedure.

Technical domain Mobile · Web frontend · Backend and APIs · Data and analytics · Cloud and infrastructure · DevOps and CI/CD · Security · QA and testing · Architecture and design · Other or general Routes knowledge to the right successor and gives per-domain coverage profiles. 6. Research Method and Data Sources

Primary data: public developer–LLM corpora

  • WildChat-1M (Zhao et al., 2024): real ChatGPT conversations with GPT-3.5 and GPT-4, filtered to programming topics. Gated on Hugging Face; research licence.
  • DevGPT (Xiao et al., 2024): ChatGPT conversations shared by developers in GitHub issues, pull requests, commits and Hacker News. Repository metadata provides weak domain labels for free.
  • Agent trajectories: public SWE-agent and OpenHands runs on real repositories (Yang et al., 2024; Wang et al., 2024). The only public data that resembles agentic development with tool calls.

Transfer-test data

  • A small sample of the team's own Claude Code, Cursor or Copilot logs, used with written consent of each member
  • Hand-labelled, between one and two hundred segments
  • Used only to test the public-trained model, never for training

Course materials

  • Lecture 1: Introduction to Project Management
  • Lecture 2: Data Science Life Cycle and Process Models
  • Lecture 3: Research Design and FAIR Principles
  • Lecture 4: Proposal Writing, Literature Review, Referencing
  • Lecture 5: Task and Project Management

Method summary

  • Quantitative, experimental: supervised multi-label classification with LLM weak supervision and a human-annotated test set
  • Knowledge distillation framing: small student model against a large teacher
  • Mixed-method evaluation: metrics plus a small successor task
Known limitation: public chatbot logs are a proxy for an organisation's own logs. The transfer test on consented team logs is the planned answer to this limitation and must not be dropped.

8. Recommended Scope for the Research Project

The project delivers a trained and evaluated knowledge classifier as its research contribution, wrapped in a focused prototype pipeline: filtering, labelling, modelling, extraction, storage, retrieval and a lightweight agent interface. The knowledge graph remains lightweight, MCP delivery is a thin layer over the retrieval service, and a dashboard is optional. Live capture of developer logs is documented as future work.

If time runs short, the classification experiment, the agreement study and the transfer test are protected. The successor task and the graph layer are the first things to scale down, and the report says so explicitly.
