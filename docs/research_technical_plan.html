Detailed Technical Plan

AI Knowledge Retention Agent – Python-first research prototype: data preparation, two-axis labelling, classifier training and evaluation, then knowledge extraction, retrieval and reuse

Version 2.1 · Revised 11 November 2026 · Companion documents: Research Plan, Detailed Architecture Plan · Code: knowledge-retention-ml

1. Project Goal

Build a proof-of-concept AI knowledge retention system whose research core is a trained classifier. The classifier learns, from public developer–LLM conversations, to identify knowledge-bearing segments and label them by technical domain and knowledge type. Its output drives extraction of knowledge cards, which are stored, retrieved and delivered to a successor through an AI agent.

The prototype must demonstrate:

  • acquisition, filtering and preprocessing of public developer–LLM corpora
  • exploratory analysis and topic discovery
  • two-axis labelling with LLM weak supervision and a human gold set
  • training and comparison of classifiers against baselines, with ablations and significance tests
  • a transfer test of the trained model on consented agentic development logs
  • knowledge extraction, storage, semantic retrieval and agent delivery
  • handover packs per person and per project, built from stored cards
  • evaluation of classification, retrieval and successor usefulness

The work is organised along the ML project lifecycle (Research Plan, section 5): one code module and one notebook per stage, run on Colab, with deployment, monitoring and retraining out of scope.

2. Why Python

Technical fit

  • The whole modelling stack lives here: scikit-learn, PyTorch, Hugging Face transformers, sentence-transformers
  • First-class dataset tooling for gated Hugging Face corpora
  • Vector stores, FastAPI and the MCP SDK all have Python APIs

Research fit

  • Notebooks for exploratory analysis and result plots
  • Reproducible experiment runners with fixed seeds and configs
  • Standard metric libraries that examiners recognise

Recommended choice

  • Python 3.11+, managed with uv or poetry
  • One package per module, shared schema module
  • Experiments as config-driven scripts, not hand-run cells

4. System Modules

4.1 Data acquisition

  • Accept licences and download WildChat-1M, DevGPT and agent trajectory datasets
  • Write a manifest with dataset version, date, licence and row counts
  • One loader per dataset emitting the shared Conversation schema
  • Fill author, role, project and date where the source provides them; project from the linked repository
  • Sample seeded random row groups rather than the first rows; agent-run files are sorted by repository, so take a few random runs from each row group to cover many projects

4.2 Filtering

  • English only, toxicity flag false; at least two user–assistant exchanges for WildChat (single-question DevGPT shares are kept)
  • Relevance (WildChat): keyword rules for programming and requirements; hand-check two hundred kept items and report precision with a 95% interval; add a zero-shot classifier only if precision is low
  • Keep agentic trajectories regardless of turn count since they are all technical

4.3 Preprocessing

  • MinHash near-duplicate removal at conversation level
  • Whitespace and unicode normalisation; keep code blocks; drop system messages
  • Segment into exchanges with the preceding exchange as context: a user–assistant pair in chats, a tool observation and the agent's next action in agent runs; at most ten evenly spaced segments per conversation; truncate to the model limit
  • Own logs are redacted first: rule-based removal of secrets and personal data plus a team list of names; a human skim follows

4.4 Exploratory analysis

  • Distributions of turns, token lengths, sources and modalities
  • BERTopic clusters to describe themes and sanity-check the domain taxonomy: each topic gets a keyword domain hint, and a large share of topics with no matching domain points to a missing label
  • Estimated share of knowledge-bearing segments from a labelled sample

4.5 Labelling

  • Codebook for both axes with definitions, examples, near-misses and observable cues
  • LLM weak labelling with structured output over the training pool
  • Human gold set labelled by two members with an overlap subset; Cohen's κ; adjudication

4.6 Modelling and experiments

  • Config-driven experiment runner with fixed seeds and conversation-level splits
  • Features built after the split: TF-IDF fitted on training texts only, fixed sentence embeddings, both with and without the context turn; token lengths checked against the 512-token model limit (inputs are cut context-first)
  • Baselines, fine-tuned multi-label transformer, SetFit few-shot variant
  • Ablations, learning curve, teacher comparison, metrics written per run

4.7 Model registry and classification service

  • Versioned weights, config, thresholds, validation and gold metrics, and a model card generated from the gold results; registration chooses the model on validation and is refused for runs not evaluated on gold
  • Every run records its git commit, library versions and data fingerprints, and an index lists all runs
  • Service loads the registered model and scores segments on CPU in resumable batches, for every model type (linear baselines and the fine-tuned transformer)
  • Emits per-label probabilities, the decided labels and a knowledge-bearing flag, plus speed per 1,000 segments for the comparison with the teacher

4.8 Extraction

  • Claude summarises flagged public segments into typed knowledge cards; own-log segments use a local extractive backend
  • Card template chosen by knowledge type; domain labels attached
  • Faithfulness check: evidence quoted verbatim from the source and at least half of the summary's content words found in the source; cards failing either are rejected with the reason; a decision label without a stated decision is dropped, not the whole card

4.9 Storage and retrieval

  • SQLite for cards, labels, provenance and consent records
  • Card embeddings searched exactly with NumPy (cosine); retrieval filtered by domain, knowledge type, person, role, project and date
  • Deleting a person removes their cards from the database, the vectors and the graph
  • NetworkX graph of problem → decision → tool → domain edges with optional one-hop expansion

4.10 Agent and delivery

  • Accept a question, retrieve cards, answer with citations to cards and source turns
  • FastAPI REST endpoints for ingestion, classification, retrieval and query
  • MCP server exposing a query tool so a successor asks from their own AI client
  • Handover pack generator: decision log in date order, procedures, domain notes, context and constraints, per person or project

4.11 Transfer test

  • Consented sample of team members' Claude Code, Cursor or Copilot logs
  • Secrets and personal data redacted; one to two hundred segments hand-labelled
  • Final registered model scored once, enforced by a lock: a re-run needs a written reason and is recorded
  • Macro-F1 drop reported with a 95% CI against the whole gold set and against its agentic part (own logs are agent sessions); per-label F1, label-frequency and length shift; the report holds ids and numbers only

4.12 Evaluation

  • Classification metrics with confidence intervals and significance tests
  • Retrieval metrics on a hand-verified query set
  • Small successor task with and without knowledge cards

7. Labelling Protocol

Taxonomy

  • Domain, multi-label: mobile · web frontend · backend and APIs · data and analytics · cloud and infrastructure · DevOps and CI/CD · security · QA and testing · architecture and design · business and requirements · general programming · other
  • Not labels: person, role and project are recorded at ingestion and never predicted
  • Knowledge type, multi-label: domain · procedural · decision · contextual · none

Weak labels

  • About ten thousand segments labelled by Claude Opus 5.5 using the codebook as a cached system prompt, schema-constrained JSON output and low effort, through the Message Batches API at half price; estimated $35–$105 in total
  • Raw responses stored; a random hundred hand-checked to estimate label noise
  • Repository metadata from DevGPT used as a second weak signal for domain

Gold labels

  • About four hundred segments, stratified by source and modality
  • Two raters each label all; Cohen's κ per axis; disagreements adjudicated by a third member
  • κ below 0.6 triggers one codebook revision and relabel, both reported

Splits

  • Training and validation drawn from weak-labelled segments, split by conversation id within each source (seeded, ten per cent of conversations to validation), with an automatic check that no conversation appears in two splits
  • Test is the gold set only; every conversation that contains a gold segment is excluded from training
  • Transfer set is scored once with the final model

8. Experiment Design

RunModelPurposeHypothesis
B0Majority classFloor—
B1TF-IDF + logistic regressionLexical baselineH1

M2SetFit on up to fifty gold examples per class, cross-fitted: five conversation folds of the gold set, each predicted by a model trained on the other foldsHow little human labelling is enoughLabelling budget

Metrics: macro-F1 and per-class precision and recall on the gold set, confusion matrices, and bootstrap 95% confidence intervals that resample whole conversations (segments of one conversation are correlated). Comparisons use a paired bootstrap on the same resamples: M1 against B1 and B2 (H1), M1 against A1 (H3), and for H2 a non-inferiority check that the lower bound of M1 minus T is above −0.05. Model selection uses the weak-label validation split; reported numbers come only from the gold set. Tuning (Stage 10) is done on validation only: the regularisation strength of the baselines, the best epoch of M1, and one decision threshold per label; predicted labels follow the codebook rules (none alone, at least one label per axis).

10. 4-Week Development Plan, Two Streams

Four members work in two streams of two. The modelling stream produces the research result; the system stream builds the application that consumes it. Members swap onto labelling in weeks one and two so everyone contributes gold labels.

1 Accept licences, download corpora, write manifest. Filtering, dedup, segmentation. EDA and BERTopic. Codebook v1. Gold labelling starts. Lock Conversation, Segment, Label and Card schemas. Repo skeleton, config, tests. SQLite and vector store set up. Loader adapters. Schemas locked; filtered corpus; codebook v1
2 LLM weak labelling of the training pool. Gold set complete, κ reported, codebook revised if needed. Baselines B0 to B2. Extraction prompts and card templates. Faithfulness check. Embedding and indexing of mock cards. FastAPI skeleton. Gold set with κ; baseline results
3 Fine-tune M1 on Colab. SetFit M2. Teacher run T with cost and latency. Ablations A1 and A2. Classification service loads registered model. Retrieval with label, person, role and project filters. NetworkX graph. Agent with citations. MCP tool. Registered model; end-to-end query works

Handover packs per project and per person. Retrieval evaluation. Successor task with a few participants. Demo and documentation. Results tables; demo; report draft
Protected if time runs short: gold set and κ, baselines, M1, transfer test. First to scale down: successor task, graph expansion, Streamlit knowledge map.

11. Evaluation Plan

Taxonomy and labels

  • Cohen's κ per axis on the rater overlap
  • Estimated LLM label noise from a hand-checked sample
  • Label distribution per source and modality

Classifier

  • Macro-F1, per-class precision and recall, confusion matrices
  • Conversation-level bootstrap confidence intervals; paired bootstrap M1 versus B1, B2 and A1; non-inferiority of M1 against the teacher (H2)
  • Learning curve and context ablation
  • Cost and latency per thousand segments, M1 versus the LLM teacher

Transfer

  • Macro-F1 on consented own logs versus the public gold set
  • Error analysis by modality and domain

Extraction and retrieval

  • Faithfulness of cards to source segments: automatic check on every card, plus a human spot check of 50 cards with a 95% interval
  • Recall@k and MRR on a hand-verified question set: questions written in the checker's own words (not card titles), every relevant card listed; 95% bootstrap CIs
  • Whether label filters improve retrieval over plain semantic search (paired difference in MRR with CI); graph expansion reported as extra context, since it is appended after the top results

Successor usefulness

  • Participants answer questions about unfamiliar work with and without the knowledge system (raw logs only), counterbalanced so every question is answered in both conditions
  • Answer quality rated blind on a 1–5 rubric (answers shuffled, condition hidden); time to answer recorded; compared within participants with a Wilcoxon signed-rank test
  • Small sample, reported as indicative

13. Deliverables

  • Filtered, deduplicated and segmented corpus with a dataset manifest
  • Exploratory analysis notebook with topic clusters and distributions
  • Codebook, gold-labelled set and agreement statistics
  • Trained classifier with weights, config, metrics and a model card
  • Results tables, learning curve, confusion matrices and error analysis
  • Transfer-test report on consented agentic logs
  • Knowledge extraction pipeline and card store with provenance
  • Retrieval service and ask-predecessor agent with REST and MCP delivery, filterable by person, role and project
  • Handover packs per person and per project
  • Evaluation report covering classification, retrieval and successor usefulness
  • Optional: knowledge map of coverage and single-person dependency, with no ranking of individuals
The research claim rests on the classifier results and the transfer test. The agent is the demonstration of how those results are used.
